## 3. Context

The goal is a readable, correctly wired reference project that shows how a modern data engineering stack fits together:

- a synthetic upstream source that streams events on a clock you can accelerate, and injects simple faults;
- a pipeline that consumes that stream, logs what it consumes, lands it, transforms it and analyzes it.

The emphasis is on plumbing: config files, entry points and the connections between components, all commented.

The faults are transparent and configurable. A ground-truth fault log supports experiments, such as measuring how many injected faults the pipeline actually catches.

## 4. Pretext: a city bike-share network

Why this domain fits the stack:

- **Two different kinds of stream.**
  - Lifecycle events (`trip_started` → `trip_ended`). These call for pairing, stream-stream joins and orphan detection.
  - Periodic state snapshots (`station_status` every 5 simulated minutes). These call for windows, gap detection and flatline detection.
- **Slowly changing reference data** (stations, bikes). It arrives through REST pulls, which motivates a dbt snapshot (SCD2).
- **A strong daily and weekly rhythm** (commute peaks, a quiet night, weekends, rain). Fast-forwarding makes these patterns visible within minutes.
- **Intuitive faults** that map onto real data quality issues.
- **Real-world analogs:** GBFS station feeds, and Wikimedia EventStreams (an SSE stream feeding Kafka).

**The simulated world**

- ~40 stations in a fictional city. Each has a lat/lon, a capacity of 15 to 40 docks, and a zone: residential, business, transit or leisure.
- ~600 bikes, mechanical or electric.
- **Demand:** a Poisson process per station. The rate is multiplied by hour-of-day, weekday, zone and weather factors.
- **Destinations:** a zone-pair matrix combined with distance decay.
- **Trip duration:** distance ÷ speed, plus noise.
- **Rebalancing:** a periodic job moves bikes from full stations to empty ones.
- **Volume:** ~18k events per simulated day at scale 1, configurable.

## 6. Key design decisions

- **Long-running streaming work runs as services, not Airflow tasks.**
  - Airflow orchestrates bounded batches.
  - Compose `restart:` policies supervise the bridge and Spark. In production, Kubernetes would play that role.
- **Kafka is the fan-out point.**
  - Spark and the DuckDB loader are independent consumers with independent offsets.
  - Replay and backfill therefore come for free.
- **Each layer owns one path.**
  - Spark owns the hot path: continuous detection.
  - DuckDB and dbt own the analytical record.
  - Spark reaches DuckDB only through Parquet files and the Kafka alerts topic. It never writes to the DuckDB file directly.
- **DuckDB allows only one writer at a time.**
  - Every Airflow task that writes to DuckDB uses the pool `duckdb`, which has one slot.
  - After each dbt build, a checkpointed serving copy is published by atomic rename. Readers use that copy and never run into the lock.
- **ELT.**
  - Raw tables hold the envelope columns plus the payload as JSON.
  - Typing and parsing happen in dbt staging, so schema drift never breaks landing.
- **Exactly-once into DuckDB.**
  - The loader stores its Kafka offsets in DuckDB, in the same transaction as the data.
  - It also commits offsets to Kafka, but only so consumer lag shows up in the console.
- **Three clocks, kept explicit.**
  - `event_time` (simulated): when the event happened.
  - `emitted_at` (simulated): when the source sent it.
  - `ingested_at` (wall clock): when the pipeline landed it.
  - Spark windows and watermarks use `event_time`. dbt freshness uses `ingested_at`. Airflow schedules on wall-clock time.
- **Event encoding.**
  - JSON with a versioned envelope.
  - No Schema Registry, to keep the stack light. It is listed as an extension.

  ```json
  {"event_id":"uuid","event_type":"trip_started","schema_version":1,"seq":1234,
   "event_time":"…","emitted_at":"…","payload":{…}}
  ```

## 7. Faults

Each fault is transparent:

- it has a rate in the config file;
- it can be toggled, or triggered once, through the admin API;
- every injection is recorded in the ground-truth fault log.

| fault | what the source does | caught by |
|---|---|---|
| duplicate | re-emits an event with the same `event_id` | Spark dedup counter; dbt staging dedup and metric |
| late_event | delays emission by 30–180 simulated minutes | Spark lateness and watermark drops; dbt lateness mart |
| schema_drift | renames or mistypes a payload field | bridge contract validation → DLQ |
| impossible_status | reports bikes_available > capacity, or < 0 | Spark rule joined to stations → alert; dbt test (warn, failures stored) |
| frozen_station | a station repeats an identical status while trips occur there | dbt (LAG, joined to trips); Spark windowed flatline |
| silent_station | a station stops reporting for 1–6 simulated hours | dbt gap analysis |
| teleport | a trip ends far away, impossibly fast (> 45 km/h) | Spark stream-stream join → alert; dbt `fct_trips` flag |
| orphan_trip | a start without an end, or an end without a start | Spark outer join after the watermark; dbt `int_trips` |
| stream_stall | the whole stream pauses, then flushes its backlog | Kafka lag in the console; dbt source freshness |

`mart_detection_scorecard` joins detections to the fault log and gives precision and recall per fault.

## 8. Components

### `source/`: FastAPI, package `bikeshare_sim`

- **`clock.py`**
  - `sim_now = anchor_sim + (wall − anchor_wall) × speed`.
  - Pause, resume and speed changes re-anchor the clock.
  - `advance(Δ)` fast-forwards: the events for Δ are generated as a burst.
- **`world.py`:** stations, bikes, zones, demand profiles and the weather process.
- **`engine.py`**
  - Advances in fixed simulated steps of 10 s up to `sim_now`, so output is deterministic for a given seed at any speed.
  - Keeps a heap of pending trip ends.
  - Emits status snapshots and runs rebalancing.
- **`faults.py`**
  - Injectors form a post-processing layer: truthful events go in, a corrupted emission comes out.
  - Each injector is one small class that also writes to the fault log.
- **`api.py`**
  - The lifespan hook starts the engine loop.
  - A ring buffer of recent events serves SSE resume and `GET /v1/events?after_seq=` replay.
  - SSE frames are written by hand, so the wire format is readable.
- **`schemas.py`:** Pydantic models, which form the published contract (OpenAPI at `/docs`).
- **State:** snapshots go to `data/source/`, so the simulation resumes after a restart.
- **Config:** `config/source.toml` holds the seed, scale, clock start and speed (default 60× = 1 simulated hour per real minute), status interval and fault rates. Every entry is commented.

### `ingest/`: the bridge (SSE → Kafka)

- **SSE client:** httpx streaming, with reconnect and backoff.
  - It resumes with `Last-Event-ID`, keeping the last seq in `data/bridge/`.
  - Delivery is at-least-once, so downstream dedup handles duplicates.
- **Validation:** Pydantic contract models owned by the consumer. Producer and consumer share a contract, not code. Invalid events go to `bikeshare.dlq.v1` with the error attached.
- **Producer:** confluent-kafka, idempotent, `acks=all`, zstd compression.
  - Trips are keyed by `bike_id`; status events by `station_id`.
  - Headers carry `ingested_at` and `schema_version`.
- **Logging:** structured JSON logs plus a periodic throughput summary: counts per type, DLQ count and last seq.

### Kafka

- `apache/kafka` 4.x, running KRaft on a single node.
- Two listeners: `kafka:9092` for containers and `localhost:9094` for the host. The config explains why.
- A one-shot `kafka-init` service creates the topics explicitly: 3 partitions, 7-day retention. Auto-create is disabled.
- Redpanda Console runs on `:8081`.

### `streaming/`: Spark 4.x Structured Streaming

- Runs in its own container in `local[*]` mode, standing in for a cluster. Changing the master is a one-line config change.
- A custom image based on `apache/spark` (python3 variant) resolves the Kafka connector at build time, so no network is needed at runtime.
- `conf/spark-defaults.conf` is mounted and commented. It covers the connector, a small shuffle partition count, the RocksDB state store and the UI.
- **Entry point `jobs/stream_analyzer.py`** reads the topics, parses them with `from_json` and explicit schemas, then applies a watermark and `dropDuplicatesWithinWatermark`. It then runs these queries:
  1. **Status rules:** impossible values, and flatlines found with windows. Station reference data comes from the source API, is refreshed periodically and is broadcast-joined.
  2. **Trip pairing:** a stream-stream full outer join with time bounds, producing teleport and orphan alerts.
  3. **Station metrics:** per station, every 15 minutes, appended to `data/lake/station_metrics/` as Parquet once each window closes.
  4. **Alerts:** written to the Kafka topic `bikeshare.alerts.v1`.
- Checkpoints go to a persistent volume, one per query.
- `rules.py` holds pure DataFrame → DataFrame functions, unit-testable with local pyspark.

### `orchestration/`: Airflow 3.x (LocalExecutor, Postgres metadata DB)

- **Image:** `apache/airflow:3.x-python3.12`, plus confluent-kafka, duckdb and pyarrow.
  - dbt-duckdb goes in a separate `/opt/dbt-venv` to avoid dependency clashes.
- **Connections and variables** are set as environment variables, e.g. `AIRFLOW_CONN_BIKESHARE_API` and `AIRFLOW_CONN_KAFKA_DEFAULT`.
- **Pool:** `duckdb` has 1 slot and is created by `airflow-init`.
- **Auth:** SimpleAuthManager with all users as admins, for local use.
- **DAGs:**
  - **`stream_landing`** runs every 5 minutes. For each topic it runs a bounded batch:
    - snapshot the end offsets, then consume up to them;
    - write `raw.<topic>` rows, the new offsets and an audit row (`raw._ingest_batches`) in one DuckDB transaction.
    - Outlet: Asset `duckdb://bikeshare/raw_stream`.
  - **`api_extract`** runs every 15 minutes. It pulls:
    - stations and bikes as snapshots;
    - weather, incrementally, by a simulated-time watermark;
    - the fault log.
    - Everything goes to `raw.*`. Outlet: Asset `duckdb://bikeshare/raw_api`.
  - **`dbt_transform`** is scheduled on the `raw_stream` asset. It runs `dbt source freshness`, then `dbt build`, then `dq_report`, then `publish_serving_copy`.
    - `dq_report` logs the scorecard and the failing tests read from `run_results.json`.
- **`include/`** holds shared helpers:
  - `kafka_to_duckdb.py`;
  - `duckdb_io.py`, the one place that defines the DB path and connection handling.

### `transform/`: dbt-duckdb

- **Profile:** `profiles.yml` lives in the project and reads the DB path from `DUCKDB_PATH`. The same project therefore runs from Airflow and from the host.
- **Sources:**
  - `raw.*`, with freshness checks on `ingested_at`;
  - external Parquet `lake.station_metrics`, written by Spark.
- **Staging (views):** typed extraction from the payload JSON, dedup on `event_id`, lateness.
- **Snapshot:** `snap_stations`, SCD2 on capacity, name and active status.
- **Intermediate:** `int_trips_paired`, `int_status_gaps`, `int_status_flatlines`.
- **Marts:**
  - `dim_stations`
  - `fct_trips` (incremental)
  - `mart_station_usage_hourly` (with weather)
  - `mart_data_quality_daily`
  - `mart_detection_scorecard`
  - `mart_pipeline_health`
- **Tests:**
  - generic tests, plus a custom generic `within_range`;
  - singular data quality tests with `severity: warn` and `store_failures`;
  - one dbt unit test on trip pairing;
  - an enforced contract on one mart.
- No external dbt packages, so there is no network dependency at runtime.

## 10. Environment

- **Local:** a uv-managed `.venv` (Python 3.12) built from one workspace lockfile. `/opt/venvs/pyDS` stays untouched.
- **Runtime:** Docker Compose. Docker 29 and Compose v5 are installed. Local Java 21 is only needed for the optional local pyspark tests.
- **Versions:** pinned at implementation time to the current stable releases (Airflow 3.x, Spark 4.x, Kafka 4.x). DuckDB is pinned to the same version in the Airflow image and the local venv, because the storage format must match.
- **Budget:**
  - ~5 GB of images; 15 GB of disk is free.
  - ~6–8 GB of RAM with every profile running; 11 GB is available.
  - Compose profiles let you run a subset.
- Containers write to `./data` as the host UID/GID (1001:1001), so no root-owned files appear.

## 11. Commenting conventions

- Every config file starts with a header saying who reads it and what it wires.
- Each wiring point is commented on both ends. Example: `KAFKA_BOOTSTRAP=kafka:9092` in compose, and the place in the bridge that reads it.
- Each entry-point module has a docstring covering:
  - its role in the flow;
  - what is upstream and downstream;
  - how to run it on its own.

## 13. Verification

- **`make test`** runs pytest on:
  - clock math;
  - determinism for a given seed;
  - each fault's signature;
  - SSE parsing and resume;
  - contract validation and DLQ routing;
  - Spark rules on small DataFrames.

  It also runs `dbt build`, including the dbt unit tests.
- **`make up`, then `make smoke`**, checks in order:
  1. the source is healthy;
  2. each topic has messages;
  3. the Spark queries are active, and `make fault f=teleport` produces an alert;
  4. DAG runs are triggered;
  5. the DuckDB marts are not empty;
  6. the scorecard shows the injected fault as detected.
- **Manual experiment:** run `make ff h=24`, then watch:
  - lag and backpressure in the Console;
  - batch durations in the Spark UI;
  - late-event counts in the data quality mart.
